The problem with an agent demo

A polished answer does not prove that an agent can operate a business workflow. The difficult questions appear after the demo: Which path did it take? What was it allowed to write? Where must it stop? What happens when data is missing? Can an operator reconstruct the decision?

I built Agent Services around those questions. The service contract—not a model prompt—is the governing object. Models can reason inside that boundary, but they do not own authority.

New work does not have to fit the catalogue

A visitor can describe a problem in their own words. The Lab compares it with the 37 bases. A strong match opens the relevant service; an unmatched brief produces a proposed tailored blueprint. That suggestion is not silently promoted into a service. I inspect it, modify the scope, remove unsafe authority, define evidence and approve or reject it before private customer engineering begins.

Graph engineering makes policy executable

Every service has its own topology. A graph can fan out to specialists, join evidence, branch on a validation result, stop at a human gate, reject an unsupported input or finish automatically on a reversible clean path. This is why the system does not flatten all services into the same six-stage animation.

The graph is not a reference diagram beside the work. It is the policy model the work must follow.

Harness, service evaluation and Eval Hub are different

Harness

Runs authored cases and records the path, tools, gates and outcomes.

→

Service evaluation

Judges whether this contract and overlay satisfy their release criteria.

→

Eval Hub

Tracks independent quality and safety baselines across VVDex products.

This separation prevents a passing model score from being mistaken for a working service. A service must follow its graph, respect authority and produce valid evidence as well as meet evaluation thresholds.

Trace, evidence and human authority

A trace records the route through the workflow. Evidence records what supports the result: inputs, checks, decisions, tool responses, reviewer identity where applicable and terminal receipts. Human approval is scoped to a named action; it is not a general permission for the agent to continue doing whatever it wants.

For example, the Document Operations sample automatically records a clean, reversible invoice path but stops an amount, bank-detail or purchase-order mismatch. Approval authorizes only the specified exception record. Rejection preserves the source and reason without posting. Payment is outside that workflow.

Reviewed memory closes the loop

Raw traces do not automatically become durable truth. Verified outcomes, approved corrections and versioned decisions can be reviewed before returning to memory. That gives later agents useful continuity without allowing one mistaken run to contaminate the operating model.

What is live—and what remains customer work

The public Lab and all 37 authored routes are live as an unlisted, noindex demonstration surface. The workflows, graph topologies and deterministic simulations are inspectable. A public sample is not a customer acceptance test.

Production specialization still requires the customer’s real systems, data contracts, permissions, security review, success thresholds and operator acceptance. Those are selected and controlled privately during implementation.

The outcome

Agent Services connects the part a prospective customer can safely see with the part an operator must privately control. The public Lab explains the work. The private Studio governs how it is specialized. Graphs bound execution, harnesses exercise it, evaluation challenges it, evidence proves it and reviewed memory improves the next version.
